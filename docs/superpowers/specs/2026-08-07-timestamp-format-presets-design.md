# タイムスタンプ`format`の利便化(プリセット/strptime対応) 設計

## 概要

`rules.yaml`のtimestampフィールド`format`は、現状Goの参照時刻レイアウト文字列(`"2006-01-02T15:04:05Z07:00"`のような書き方)しか受け付けていない。これは表現力は高いが、多くのユーザーにとって直感的でない(Goのマジックリファレンス日時を覚える必要がある)。

`format:`に以下の3種類の書き方を共存させ、既存のGoレイアウト文字列による指定は完全に維持したまま、より馴染みのある指定方法を追加する:

1. **プリセット名**(`iso8601`、`unix`など): よく使われる形式を名前で指定
2. **strptime記法**(`%Y-%m-%d %H:%M:%S`など): Unix系ツールで馴染みのある書き方
3. **生のGoレイアウト文字列**(現状のまま): 上記でカバーできない任意の形式への逃げ道

## 目的

- ログでよく使われるタイムスタンプ形式(ISO8601、RFC822/2822、Unix epoch、CLF、syslog、Pythonロガーのデフォルト形式)を、名前1つで指定できるようにする
- strptime系の`%`記法を使い慣れたユーザーが、Goのレイアウト文字列を新たに覚えずに済むようにする
- 既存の`rules.yaml`(生のGoレイアウト文字列を使用)は無変更で動作し続ける

## Non-goals

- POSIX strptimeの全ディレクティブ完全対応(`%j`(年間通日)、`%U`/`%W`(週番号)などGoレイアウトに1対1で変換できないものは対象外。使用された場合は起動時エラーにする)
- 生のGoレイアウト文字列自体の妥当性を起動時に検証すること(現状通り、実際の値でパースするまでエラーが出ない)
- タイムゾーンデータベースを使った named timezone(`%Z`/`MST`等)の厳密な解決(Goの標準機能に依存する範囲に留める)

## `format:`の自動判別ルール

`format`文字列を以下の優先順位で解釈する:

1. **既知のプリセット名と完全一致(大文字小文字を区別)** → 対応するGoレイアウト、またはepoch解析
2. **`%`で始まる** → strptime記法として解釈し、Goレイアウトに変換
3. **それ以外** → 現状通り、生のGoレイアウト文字列としてそのまま使う

この3つはいずれも最終的に「Goレイアウト文字列によるパース」または「epoch数値パース」のどちらかに解決される。生のGoレイアウト文字列を直接書く既存の使い方は、判定ルール3にそのまま該当するため後方互換性が保たれる。

## プリセット一覧

| プリセット名 | 内部Goレイアウト / 解析方式 | 備考 |
|---|---|---|
| `iso8601` | `2006-01-02T15:04:05.999999999Z07:00` | `rfc3339`のエイリアス。小数秒はあってもなくても可 |
| `rfc3339` | 同上 | `iso8601`のエイリアス |
| `rfc822` | `02 Jan 06 15:04 -0700` | 数値タイムゾーンオフセット版。named timezone(`MST`)はGoでの解決が信頼できないため不採用 |
| `rfc2822` | `Mon, 02 Jan 2006 15:04:05 -0700` | メールヘッダ`Date:`相当(Goの`RFC1123Z`と同一) |
| `clf` | `02/Jan/2006:15:04:05 -0700` | Apache/nginxのCommon Log Format |
| `syslog` | `Jan _2 15:04:05` | 年なし。伝統的なBSD syslog形式(1桁の日はスペース埋め: `Aug  7`) |
| `pylog` | `2006-01-02 15:04:05,999999999` | Pythonロガーの`%(asctime)s`デフォルト形式(カンマ区切り小数秒) |
| `unix` | epoch秒(整数/小数) | |
| `unix_ms` | epochミリ秒(整数) | |
| `unix_us` | epochマイクロ秒(整数) | |
| `unix_ns` | epochナノ秒(整数) | |

年なしのプリセット(`syslog`)は、既存の年補完ロジック(後述)がそのまま適用される。

## strptime変換表

`%`で始まる`format`は、以下の対応表に従って文字単位でGoレイアウト文字列に変換する。表にないディレクティブが出現した場合は、rules.yaml読み込み時点でエラーにする(未実装の挙動を黙って無視しない)。

| ディレクティブ | 意味 | Goトークン |
|---|---|---|
| `%Y` | 4桁年 | `2006` |
| `%y` | 2桁年 | `06` |
| `%m` | 月(2桁) | `01` |
| `%d` | 日(2桁) | `02` |
| `%H` | 時(24h表記) | `15` |
| `%I` | 時(12h表記) | `03` |
| `%M` | 分 | `04` |
| `%S` | 秒 | `05` |
| `%f` | 小数秒(可変桁数) | `999999999` |
| `%z` | UTCオフセット | `-0700` |
| `%Z` | タイムゾーン名 | `MST` |
| `%a` / `%A` | 曜日(省略形/フル) | `Mon` / `Monday` |
| `%b` / `%B` | 月名(省略形/フル) | `Jan` / `January` |
| `%p` | AM/PM | `PM` |
| `%%` | リテラルの`%` | `%` |

`%`以外の文字(区切り文字、空白、カンマなど)はそのままリテラルとしてGoレイアウトに引き継がれる。

### `%f`とカンマ区切り小数秒について

Goの`time.Parse`は、レイアウト側の小数秒区切り文字が`.`であっても、**入力側が`.`と`,`のどちらでも受理する**という仕様がある(検証済み)。`%f`を可変長トークン`999999999`に変換しておけば、区切り文字がカンマの入力(Pythonロガーのデフォルト`asctime`など)も追加のコードなしで扱える。`pylog`プリセットもこの仕組みの上に構築されている。

## アーキテクチャ: 読み込み時に一度だけ解決する

`Rule.Pattern`を`rules.Load()`時に一度だけ`regexp.Compile`して`Rule.Regexp`にキャッシュしている既存の設計と同じ考え方を適用する。`Field.Format`をログ1行ごとに文字列解析し直すことはしない。

- `internal/rules`に`ResolveFormat(format string) (TimeFormat, error)`を追加する
  - プリセット名/strptime/生Goレイアウトの自動判別はここで一元的に行う
  - `TimeFormat`は`{ Layout string; EpochUnit time.Duration }`。`EpochUnit == 0`なら`Layout`を使った通常のGoレイアウトパース、`0`以外ならepochパース(値 × `EpochUnit`でナノ秒に変換)
- `rules.Load()`で、timestamp型の各フィールドに対して`ResolveFormat`を呼び、結果を`Field`に持たせる(`Rule.Regexp`と同じ位置づけのキャッシュ)
- `internal/parse`の`parseTimestamp`/`convertValue`は、解決済みの`TimeFormat`を使うだけになり、`Format`文字列を直接見ない
- 年なしフォーマットの判定(Goの年トークン`2006`が含まれるか)は、解決済みの`Layout`に対して行う。プリセット/strptime/生レイアウトのどの経由でも同じロジックがそのまま使える
- epochパースは精度に配慮する: `strconv.ParseInt`でパースできる場合は整数演算のまま単位変換する(`unix_ns`のような大きな整数値をfloat64経由にすると仮数部53bitの精度を超えて丸め誤差が出るため)。小数点を含む入力(`unix`での小数秒指定など)のみ`strconv.ParseFloat`にフォールバックする

## バリデーション(起動時)

既存の「timestamp型なのに`format`が空」チェックに加え、以下を`rules.Load()`/`Validate()`の時点で検証する:

- `ResolveFormat`が失敗する場合(未対応のstrptimeディレクティブ使用など)は、どの入力ファイルも処理せずに即座にエラー終了する(既存のfail-fastポリシーを踏襲)
- 生のGoレイアウト文字列(判定ルール3に該当するもの)は、現状通り起動時には検証しない(実際の値のパース時に初めてエラーが判明する、既存動作を維持)

## 後方互換性

- 既存の`rules.yaml`にある生のGoレイアウト文字列(例: `"02/Jan/2006:15:04:05 -0700"`)は、プリセット名にもstrptime記法にも該当しないため判定ルール3にフォールバックし、無変更で動作する
- `Field`構造体・`fields:`のYAML構文自体に変更はない(`format`の値の解釈が広がるだけ)

## テスト方針

- **`internal/rules`**: `ResolveFormat`のテーブル駆動テスト
  - 各プリセット名が期待する`Layout`/`EpochUnit`に解決されること
  - strptimeの各ディレクティブおよび組み合わせが正しいGoレイアウトに変換されること
  - 未対応ディレクティブ(`%j`など)使用時にエラーになること
  - 生のGoレイアウト文字列(プリセット名にもstrptimeにも該当しないもの)がそのまま`Layout`として通ること
- **`internal/parse`**: 既存の`timestamp_test.go`/`convertvalue_test.go`を拡張
  - epoch4種(秒/ミリ秒/マイクロ秒/ナノ秒)の正しい変換(境界値・大きな整数値での精度も含む)
  - 年なしプリセット(`syslog`)の年補完ロジック(既存の年境界テストと同様のケース)
  - `pylog`プリセットおよび`%f`を含むstrptimeでのカンマ区切り小数秒
  - `clf`プリセットが既存の生レイアウトによる同等指定と同じ結果になること
- **End-to-end(`cmd/logidx`)**: 複数のタイムスタンプ形式(プリセット・strptime・生レイアウト混在)を含むfixtureログで`logidx import`を実行し、`logidx dump`で出力Parquetのタイムスタンプ値を検証する
